Antes del teclado: ocho hábitos que cambian el resultado

Resolver un problema no empieza cuando escribes código. Empieza cuando conviertes un enunciado en una idea que puedes explicar, probar y defender.

Idea clave

No empieces buscando “qué algoritmo es”. Empieza buscando qué sabes del problema.

  1. Entiende exactamente qué se pide

    Identifica la entrada, la salida y qué cambia. Dibuja el caso: un grafo, índices sobre un arreglo, movimientos, estados o intervalos. Muchas veces “no sé resolverlo” significa todavía “no entiendo qué está ocurriendo”.

  2. Mira restricciones y límites

    Las restricciones descartan soluciones antes de programarlas. Si n = 10⁹, ni siquiera puedes recorrer todos los valores; si n = 2·10⁵, una solución cuadrática está fuera. Úsalas como pistas, no como decoración.

  3. Piensa primero en brute force

    La solución ingenua casi nunca será la final, pero revela la lógica exacta: qué decisiones existen, qué resultados cuentan y qué trabajo se repite.

  4. Calcula su complejidad

    No digas solo “es lento”. Cuenta loops, estados y operaciones. Escribe O(n²), O(2ⁿ) o la cota que corresponda y compárala con el límite.

  5. Encuentra el costo que debes quitar

    Pregunta qué parte es más cara, qué información recalculas y qué propiedad todavía no usas. Luego conecta esa necesidad con herramientas conocidas: ordenar, prefijos, búsqueda binaria, dos punteros, mapas, grafos o programación dinámica.

  6. Elige una idea y pruébala a mano

    Ejecuta tu solución sobre el ejemplo y sobre un caso pequeño propio. Si no puedes explicar cada paso sin código, la idea aún no está lista.

  7. Inventa casos nuevos

    Prueba mínimos, máximos, repetidos, ordenados, invertidos, todo igual, respuesta vacía y casos donde tu intuición pueda fallar. Los buenos casos atacan supuestos.

  8. Ahora sí: programa

    Escribe cuando ya sabes qué representará cada variable y por qué la solución funciona. Programar demasiado pronto mezcla dos problemas: diseñar la idea y corregir el código.

Restricciones y complejidad: aprender a leer las pistas

La complejidad no busca predecir el tiempo exacto. Sirve para saber cómo crece el trabajo y eliminar ideas que no pueden terminar a tiempo.

Tamaño aproximadoQué podría funcionarLectura rápida
n ≤ 20O(2ⁿ), backtracking, bitmaskPuedes explorar subconjuntos.
n ≤ 100O(n³) en algunos casosTriple loop quizá sea aceptable.
n ≤ 10³O(n²)Un millón de operaciones es razonable.
n ≤ 10⁵–2·10⁵O(n log n) u O(n)Ordenar sí; comparar todos con todos, no.
n ≤ 10⁶O(n) o casi linealCuida memoria, constantes y número de casos.
n ≈ 10⁹O(log n), fórmula o matemáticaNo puedes recorrer el rango.

Estas cotas son intuiciones, no leyes. Importan el lenguaje, las constantes, la cantidad de test cases, la memoria y el tipo de operación. Como regla mental, muchos jueces permiten alrededor de 10⁷–10⁸ operaciones simples por segundo, pero siempre debes leer el time limit.

Programación rápida, limpia y ordenada

Velocidad no significa escribir código críptico. Significa reducir decisiones repetidas, usar nombres previsibles y poder detectar errores bajo presión.

Un template corto, conocido y suficiente

Memoriza una base que entiendas completa. No llenes el template con estructuras que no usarás: más código también significa más lugares donde equivocarte.

Fast I/O, sin rituales innecesarios

ios::sync_with_stdio(false); y cin.tie(nullptr); son lo importante cuando usas cin/cout. No necesitas cout.tie(nullptr). Después de desactivar la sincronización, evita mezclar scanf/printf con streams de C++.

Aliases y constantes: intención, no decoración

Cuándo usar cada tipo

  • int: índices, tamaños moderados y valores hasta aproximadamente 2·10⁹.
  • ll: sumas, productos, distancias y respuestas que pueden superar int.
  • pii: pares como {distancia, nodo} o {valor, índice}.

Evita overflow antes de que ocurra

El resultado se calcula con el tipo de los operandos. En 1LL * a * b, el primer producto ya usa long long. Convertir después puede ser demasiado tarde.

overflow-y-módulo.cpp
int a = 100'000, b = 100'000;

ll good = 1LL * a * b;       // 10^10: correcto
ll bad  = a * b;             // overflow antes de asignar

ll product = (x % MOD) * (y % MOD) % MOD;
ll add = (x + y) % MOD;
ll sub = (x - y + MOD) % MOD;

auto, referencias y loops

Usa auto cuando el tipo sea obvio o demasiado largo; evita usarlo cuando esconda una conversión, precisión o copia importante.

recorridos.cpp
vector<int> a = {4, 1, 7};

for (int x : a) {            // copia: útil si solo lees valores pequeños
    cout << x << ' ';
}

for (int& x : a) {           // referencia: modifica el vector
    x *= 2;
}

for (const int& x : a) {     // sin copia y sin modificación
    cout << x << '\n';
}

map<string, int> frequency;
for (const auto& [word, count] : frequency) {
    cout << word << ' ' << count << '\n';
}

for (int i = 0; i < n; ++i) {
    // Usa índice cuando la posición importa.
}

Nombres que te ayudan a pensar

n, m para tamaños; u, v para extremos de una arista; i, j para índices; ans para respuesta; freq, dist, parent, visited para su función real. Un nombre un poco más largo cuesta menos que depurar una variable ambigua.

Orden recomendado dentro de solve()

Lectura → preprocesamiento → algoritmo → respuesta. Mantén cada etapa junta y evita variables globales salvo que el tamaño, la recursión o el rendimiento realmente lo justifiquen.

Debugging inteligente: buscar evidencia, no adivinar

Cuando algo falla, cambiar líneas al azar destruye información. La meta es reducir el caso hasta encontrar la primera diferencia entre lo que esperabas y lo que el programa hace.

1 · ReproduceConsigue un caso que falle siempre.
2 · ReduceHazlo tan pequeño que puedas simularlo.
3 · PrediceEscribe el estado correcto antes de ejecutar.
4 · ObservaImprime variables e invariantes con intención.
5 · AíslaEncuentra la primera línea donde divergen.

// Envía información de diagnóstico a cerr, no a cout.

Idea clave

Un buen mensaje de debug responde una pregunta concreta. “¿En qué iteración deja de cumplirse esta invariante?” es mucho mejor que imprimir todo.

Contest strategy: administrar información, tiempo y confianza

El concurso no premia el orden del PDF. Premia resolver la mayor cantidad posible con el tiempo disponible. Tu primera tarea es construir un mapa, no enamorarte del problema A.

Primera pasada: reconocer el terreno

Lee todos los problemas de forma breve. Para cada uno anota qué pide, restricciones, técnica probable, si tienes una idea y qué te bloquea. Si no aparece una ruta clara en pocos minutos, marca el estado y continúa.

Segunda pasada: elegir por valor, no por orgullo

Ataca primero

  • El problema con idea completa y baja incertidumbre.
  • El que puedes validar con casos pequeños.
  • El que desbloquea puntos rápidos o confianza.

Cambia de problema cuando

  • Repites la misma idea sin obtener información nueva.
  • Tu prueba depende de “parece que funciona”.
  • Llevas demasiado tiempo depurando sin un caso mínimo.

En papel, actualiza el mapa: leído, idea, programando, debug, enviado. Anota también el motivo del bloqueo. Así, cuando vuelvas, no comienzas desde cero.

Checklist antes de enviar

  • ¿Entendí exactamente la salida?
  • ¿La complejidad cabe en todas las pruebas?
  • ¿Alguna suma o multiplicación necesita long long?
  • ¿Los índices y límites incluyen o excluyen el extremo correcto?
  • ¿Reinicio estructuras entre test cases?
  • ¿Probé mínimo, máximo, repetidos y casos vacíos?
  • ¿El ejemplo coincide paso a paso?
  • ¿El formato tiene espacios y saltos correctos?
  • ¿Quité prints de debug en cout?
  • ¿Elegí el lenguaje y archivo correctos?
Idea clave

Un “Wrong Answer” rápido con una hipótesis clara puede enseñar. Veinte minutos de cambios aleatorios solo gastan el reloj.

Upsolving: donde el concurso se convierte en aprendizaje

Upsolving es volver después del concurso a los problemas que no resolviste —o resolviste mal— hasta entender la idea y poder implementarla sin depender de la solución.

1 · ReintentaCon tiempo, vuelve a leer restricciones y prueba tu mejor idea.
2 · ConsultaLee solo la pista necesaria. No copies código del editorial.
3 · ExplicaEscribe por qué funciona y qué costo eliminó.
4 · ReimplementaCierra la solución y prográmala desde cero; luego envíala.

Clasifica la causa real: no conocía la herramienta, no vi la observación, tuve la idea pero no pude demostrarla, implementé mal o administré mal el tiempo. Cada causa necesita una práctica diferente.

Regla práctica

Haz upsolving mientras el contexto siga fresco, idealmente dentro de las siguientes 24–48 horas. Guarda una nota corta: problema, observación clave, error propio y señal que podrías reconocer la próxima vez.

Conclusión del año

Después de algoritmos, estructuras, errores y concursos, queda una sola idea que vale la pena conservar.

Son herramientas; tú eres quien resuelve. Todo lo que vemos se agrega a lo que tú puedes hacer: no son fórmulas mágicas ni recetas.
